# Functions defined in BOTH SteamShell.ahk and SteamShell-XFE.ahk that the
# fingerprint gate has flagged as the same routine written twice, and which are
# allowed to stay that way -- each with the reason recorded beside it.
#
# Why this file exists
# --------------------
# SHARED_FUNCTIONS.txt records what IS defined once. This records what is not,
# and why. Until the gate existed there was no third state: a function was
# either shared or it was two copies nobody was counting.
#
# The gate compares a naming- and comment-blind CALL SEQUENCE, because text
# similarity cannot see duplication in this codebase. Text is exactly what gets
# changed when a copy is tidied -- rename a parameter, rewrap a DllCall, swap a
# switch for a Map -- and an audit that measured text scored ControllerBindingPretty
# at 0.26 and GetLastLines at 0.49 while both had an IDENTICAL call sequence.
# Thirty-four pairs were being read as intentional divergence. They were not
# intentional; they were unmeasured. That is the whole reason for this file: the
# ones that remain have to say out loud why.
#
# Format
# ------
#   FunctionName: the reason it must differ
#
# An entry with no reason FAILS the build. The reason is the entire value here --
# a bare name is the state this file was created to end. Delete an entry the
# moment its two copies are merged; a stale entry also fails, so the file cannot
# quietly become a list of things nobody looks at again.
#
# ONE ENTRY PER NAME, and that also fails the build now.
#
# This file used to carry PENDING headings as a separate worklist, and five names
# ended up listed twice: a PENDING reason under one heading, a contradictory
# PERMANENT one under another. Both harnesses read this file into a dictionary,
# so the later entry silently won and the PENDING half was text nothing read.
# Those five were the entire worklist. The count this file exists to drive down
# could not be seen going down.
#
# So scheduled consolidation is now recorded IN the one reason that name is
# allowed -- "...; Phase 4a's table should absorb both" -- where the gate that
# prints the reason will print the plan with it.

# ------------------------------------------------------------------------------
# PERMANENT -- the per-product seam
# ------------------------------------------------------------------------------
# SteamShell-Shared.ahk calls these precisely SO the two products can answer
# differently. Sharing them would defeat the mechanism rather than improve it.

ProductIdentity: each product names, titles and icons itself; Shared asks so it does not have to know which program it is compiled into
ProductVersionText: standalone reports a shell version and the helper build; the companion reports its own and has no helper of its own to name
ProductTrayBaseTip: the notification-area tooltip states what the program is, and they are not the same program
ProductTrayItems: the companion's tray menu has no shell controls to offer, because Xbox FSE owns the shell; the shapes differ because the menus genuinely differ
ProductSettingsScrollBar: the two Settings surfaces are separate implementations holding their scrollbar in differently named globals; revisit when Phase 4c unifies settings
ProductDataDir: where each program writes what it writes -- the shell reads a global Setup can relocate, the companion is portable and answers A_ScriptDir. Asking through the seam is what let ElevatedRtssRequestPath stop being two functions.
SettingsRegisterBuiltField: both record a field the shared builders created, and the gate scores them 1.00 because both are a push and a loop. What they push to is not the same thing: the shell keeps an ARRAY of field Maps carrying section, key and type, which its save iterates; the companion keeps a MAP from Section.Key to the control, which its accessors index. Sharing this would mean sharing the registry, and the two registries are shaped for the two different things each product does with them.
SettingsProductWireDependency: each tree wires the driver control to ITS OWN dependency pass -- SettingsEditorRefreshDependencies in the shell, SettingsRefreshDependencies in the companion -- and the body can only name one of them, which is the same shape as RecordShortcutChord below. The two passes cover different row sets and that is not drift: six of the eight rows the shared spec marks with "dependency" are "product", "standalone" and are never built into the companion's window. The other two are "product", "both" -- the RTSS overlay and frame-limiter control modes -- and both trees now honour those. This entry used to say the companion's body was deliberately empty; it was empty, but those two shared rows reached its window and did nothing, so what was recorded as a design choice was an unimplemented one.
ProductSetDialogActive: both bodies assign one global and the gate scores them 1.00 because neither calls anything -- but they assign DIFFERENT globals. The shell suppresses controller input through SettingsEditorDialogActive and the companion through SettingsDialogActive, each of which the rest of that tree already reads in several places. Merging them would mean renaming a flag across one tree to satisfy a similarity score.
ProductSettingBool: the one lookup shared code cannot do. AutoHotkey v2 cannot read a global by a name held in a variable, so QuickMenuToggleTable carries each row's section and key but never its live state, and each product answers for its own globals. The two bodies score 1.00 on call sequence because neither body CALLS anything -- both are a switch over row ids returning globals -- so the similarity is measuring the shape of a lookup table, not shared logic. They name entirely different variables and always will; the companion has no EnableDesktopBlackout and the shell has no EnableGameFocusLite. Merging them would mean declaring every setting of both products in one function, in a tree where Common must declare no globals at all.

# ------------------------------------------------------------------------------
# PERMANENT -- product vocabulary
# ------------------------------------------------------------------------------

ControllerBindingPretty: resolution logic is shared; the LABELS are deliberately not. The companion speaks Xbox FSE's vocabulary -- "Game Bar" for WinG, "Back / Escape" for Esc, "Close window" for AltF4 -- and offers TaskView, WindowsDesktop and Settings actions standalone does not, while standalone offers ControlPanel. Kept as a per-product label map behind one shared resolver.

# ------------------------------------------------------------------------------
# PERMANENT -- the privilege boundary
# ------------------------------------------------------------------------------
# BOTH products run at normal integrity, and both drive the same elevated helper
# binary through --product. The difference is a CONTINGENCY, not an architecture:
# standalone can end up elevated anyway -- an administrator Setup takeover
# re-launches it, and a user can start it as admin -- and as the shell it must
# not pass that token to TabTip, Explorer or RTSS. Its launchers therefore open
# with `if !A_IsAdmin` and then do exactly what the companion does; the ladder
# below that branch is the part the companion has no use for.
#
# Sharing standalone's version compiles calls to LaunchInteractiveApp and
# DesktopShellMatchesInteractiveUser into a program that has neither, which is a
# LOAD-time failure -- caught by the reachability check, not by review.

RunViaDesktopShell: standalone carries an A_IsAdmin contingency ladder for the case where it has been started elevated; the companion has no such case and calls ShellExecute directly
OpenTouchKeyboard: standalone reaches TabTip through LaunchInteractiveApp so that IF it has been started elevated the token is not inherited; the companion has no such path
OpenWindowsSettings: the same contingency as the two above -- standalone opens ms-settings: through LaunchInteractiveApp so an inherited admin token is not handed to the Settings app, the companion calls RunViaDesktopShell and falls back to Run. Recorded here rather than left out because the gate scores this pair 0.00 and would never have asked: five lines against five lines, sharing no calls at all, which is what a genuine privilege divergence looks like to a call-sequence comparison. Absence from this file was not evidence it had been considered.

# ------------------------------------------------------------------------------
# PERMANENT -- helper wrappers over one shared implementation
# ------------------------------------------------------------------------------
# SteamShell-Helper.ahk cannot #Include SteamShell-Shared.ahk, so those names
# necessarily exist in both. They are no longer two implementations: each is a
# three-line wrapper binding its own global to the single definition in
# SteamShell-Common.ahk. The name is duplicated; the behaviour cannot drift,
# which is what the Integer()-against-Round() split proved was worth ending.
#
# The heading said "these four names" while ten entries sat under it, and only
# six of those are helper wrappers at all -- ProductQuickMenuBlockedReason,
# QuickMenuHideThenSteamMenu and MouseWatchDisabled are ordinary tree pairs that
# happen to be small. No count is stated now, for the same reason the seam counts
# came out of the two file headers: a number in prose is a number nothing reads,
# and this one had been wrong long enough to be quoted.
#
# Entries below are therefore of two kinds -- Shared-or-Common against Helper,
# and tree against tree. The reason on each line says which.

ReadBool: three-line wrapper binding IniPath or SettingsPath to ReadIniBool in SteamShell-Common.ahk
ReadInt: three-line wrapper binding IniPath or SettingsPath to ReadIniInt in SteamShell-Common.ahk
SweepAbandonedSettingsUpdates: three-line wrapper binding IniPath or SettingsPath and ScriptPid to SweepAbandonedIniUpdates in SteamShell-Common.ahk. The companion gained it when its settings writes became staged: staging is what leaves an abandoned .update-PID.tmp behind, so a product that stages without sweeping trades one kind of litter for another. Scores 1.00 because both wrappers are one call; what they bind is the pair of globals Common may not declare.
ProductQuickMenuBlockedReason: standalone refuses to open the menu while the desktop is being restored or when it is switched off; the companion has neither state and always answers ""
InitXInput: three-line wrapper caching ResolveXInputDll in each program's own XInputDll global
HasLongBinding: three-line wrapper passing each program's ControllerMap to ControllerBindingHasLong
QuickMenuHideThenSteamMenu: the companion resolves the shortcut through SendSteamMenu rather than reading SteamMenuShortcut, so the two take their value from different places
MouseWatchDisabled: standalone stands the whole pass down while Explorer is allowed, because the desktop shell owns the cursor then; the companion has no desktop shell and gates only on the setting
SendChordSafe: three-line wrapper over SendChordReleasingModifiers in SteamShell-Common.ahk; the shared copy also declines while the companion is disabled, which the helper has no concept of
LogLine: the two trees now share one definition in SteamShell-Shared.ahk, which the helper cannot see, so its copy is the third. It is also not the same function: the helper creates the log directory and returns silently when LogPath is empty, because it can start before the directory exists and must never throw out of a logging call in an elevated process. It rotates through RotateHelperLogIfNeeded, named apart from the shared RotateLogIfNeeded precisely so the two cannot be mistaken for one.

# ------------------------------------------------------------------------------
# PERMANENT -- parallel handler families under different names
# ------------------------------------------------------------------------------
# THE CASE THAT SHOWED THE GATE HAS A BLIND SPOT, and the reason the reachability
# check now looks for bare references as well as calls.
#
# Each tree owns a family of shortcut-capture handlers named its own way:
#
#   standalone                            companion
#   RecordShortcutChord_OnKeyDown         RecordShortcutKeyDown
#   RecordShortcutChord_OnKeyUp           RecordShortcutKeyUp
#   RecordShortcutChord_TrySetMod         RecordShortcutSetModifier
#   RecordShortcutChord_GetLiveMods       RecordShortcutGetLiveMods
#   RecordShortcutChord_UpdatePreview     RecordShortcutUpdatePreview
#   RecordShortcutChord_Accept            RecordShortcutAccept
#
# RecordShortcutChord wires those up, so its body can only name one set. The
# fingerprint scored the pair 1.00 and it was shared on that evidence -- because
# every one of those names is passed as a CALLBACK, with no parentheses, and the
# call-sequence comparison only sees calls. The single thing that differed was
# the single thing the measurement could not see.
#
# In the companion the result was not a crash. AutoHotkey read the missing name
# as a local that is never assigned, warned at load, and wired the OK button to
# nothing. Renaming one family would merge these, but that is six renames in a
# tree that works, for one function; the entry is cheaper and the reason is now
# on the record.

RecordShortcutChord: each tree wires up its own handler family, named its own way, and the body can only name one set -- see the table above. MEASURED, because the note above used to claim renaming one family would merge these and that is false: the six handlers differ in SUBSTANCE, not only in name. Standalone's are consistently the larger -- 28/20, 16/8, 33/16, 38/21, 11/5 lines -- and body similarity runs from 0.94 down to 0.48. Its Accept snaps a default modifier map when the user never pressed a main key, which the companion's simply does not do. Renaming would therefore turn one divergent entry into six. The merge worth doing is adopting standalone's richer handlers into the companion, which is an input-capture behaviour change and needs testing on hardware.
ControllerReadState: what is left after the slot-discovery port and the backend-recording port, and it is one thing -- GameInput. Both trees now try RawInput first, decline to fall back when RawInput was asked for by name, record which backend answered through the shared SetActiveBackend, and finish at the shared XInputResolveController; the shell's body is a strict subset of the companion's because the companion also tries a GameInput backend in between. SetActiveBackend is no longer one of the blockers -- it is in SteamShell-Shared.ahk and both trees call it, because the shell's Health Check needs the backend that ANSWERED and used to infer it from whether RawInput was registered, which named RawInput for a pad XInput was reading. What sharing still needs is InitGameInput, GameInputReadState and ShutdownGameInput in both trees, which is a new input backend in the product that runs as the shell and wants hardware behind it rather than a review -- and the Backend setting deliberately does not offer GameInput there, because it reads all zeros outside Xbox FSE. The scan itself is already shared and was the part that mattered: reading only the configured index meant a pad Steam Input moved between slots stopped answering mid-session.
AutoMouseModeActive: the companion has no desktop mode, and that is an ARCHITECTURAL rule rather than an omission. Validate-SteamShell-XFE.ps1 asserts -notmatch 'EnableDesktopAutoMouseMode\s*:=' and -notmatch 'DesktopAutoMouseExcludeExeSet', in its own words so that reintroducing the mode 'is a decision someone has to take deliberately'. Sharing standalone's body required declaring both names in the companion, which is precisely what that rule forbids. The reason was already written down -- in the validator rather than in a comment.

# MEASURED at the 0.45 bar -- pairs the old 0.75 threshold never asked about
# ------------------------------------------------------------------------------
# Lowering the gate's bar from 0.75 to 0.45 surfaced a set of pairs that had been
# defined in both trees the whole time. Nothing had ever required a reason, so
# none of them had one. They are written up below; OpenWindowsSettings came out
# of the same sweep and is filed under the privilege boundary above, where it
# belongs by subject rather than by score.
#
# (No count is stated. The first draft of this paragraph said "these eleven" over
# ten entries, which is the defect two file headers and a section heading in this
# very file have already been corrected for. The list is the count.)
#
# Read before being written up, not scored and filed. The split is not what the
# numbers suggested: two were drift and were FIXED rather than recorded
# (TrayOpenQuickMenu's WinActivate, and QuickMenuHandleController's restatement of
# QuickMenuGoBack), and the two largest are one routine each, written twice,
# sitting comfortably under the old bar.
#
# The scores below are the reason each entry exists, not the reason it is allowed.

ApplyRuntimeTimers: 0.57, and genuinely two programs. Both stop every timer and then start the ones their settings enable, which is the whole of the similarity; the timers themselves have almost nothing in common. The shell drives MonitorShell, WindowEngineTick, the taskbar guard, the desktop blackout and launcher cleanup, and gates all of it on DesktopMode and SafeMode -- states the companion does not have. The companion drives AssistTick, Heartbeat, ObserveForeground and the controller diagnostic tick, and gates on CompanionDisabled. Sharing the stop-then-start skeleton would mean naming every timer of both products in one body. NOTE, not drift: the companion also calls RawInputProbeStart and registers PowerBroadcastMessage here, so it re-arms RawInput on every settings reload; the shell arms it once from its auto-execute section. Both work, and the companion's is the more robust of the two if RawInput registration is ever lost at runtime.
ExportDiagnosticBundle: 0.59, and the ENVELOPE is now shared. Both trees staged a timestamped directory under %TEMP%, wrote sanitised text files, zipped it through Compress-Archive and deleted the staging directory -- twice. That is ExportDiagnosticArchive in SteamShell-Shared.ahk now; each tree passes a Map of filename to content and reports success its own way, which is the part that genuinely differs (the shell writes into the Health Check and Settings status lines, the companion raises a notification). SANITISATION MOVED INSIDE the envelope, so neither tree calls SanitizeDiagnosticText any more and a file added to the map cannot forget it -- which matters for an archive a user is about to send someone. Duplicating the envelope is how the CONTENTS drifted: the companion collected display scale, HDR, backend, XInput slot and RawInput state for months while the shell collected none of it, on the product where an unreadable controller means a machine nobody can drive. Sharing the envelope does not keep the contents in step by itself; it removes the reason they were ever edited apart.

LoadControllerMappings: 0.67, and now a WRAPPER pair rather than a duplicated reader. The loop both trees carried -- seed the defaults, walk the twenty-two Button.Short/Button.Long keys, normalise a bare value to "Send:", fill the display from .Display or SendToPretty -- is one function, LoadControllerMappingsFromIni in SteamShell-Shared.ahk. The companion's version was the one kept because it was the more correct: for a bare value the shell never consulted .Display and always derived the label, so a display name stored against an unprefixed mapping was silently ignored; sharing it fixed that in the shell. What is left in each tree is the wrapper, and the shell's carries a one-time Start.Short/Start.Long migration from the schema 4 defaults that the companion never shipped and must not perform. Same shape as the ReadBool and ReadInt entries above: the name stays in both, the behaviour cannot drift, because there is only one reader.

LoadSettings: 0.47, and the low score is honest for once. The shell reads 94 keys and the companion 82, with only 33 in common, and every one of them assigns a global that Common is forbidden to declare and Shared would have to declare into both trees. The shell owns WindowManagement, GameForegroundAssist, AlwaysFocus, LauncherCleanup, MousePark, Splash and Timing; the companion owns Assist, Companion, StartupPrograms, Steam and RTSS. The 33 shared keys are a real consolidation target and the shared settings spec already tags every row "both", "standalone" or "xfe", so the data to drive it exists -- but a shared reader would still need somewhere to put the values, which is the same wall ProductSettingBool documents.
PollController: 0.31, AND THE LARGEST DUPLICATE IN THE CODEBASE -- the score is the point, not a reassurance. About 350 lines on each side, and the core is one routine: the same static button table, the same edge detection, the same long-press and chord timers, the same deadzone, the same mouse move and scroll. It is BELOW the 0.45 bar and would not be flagged even now; it is documented here voluntarily, which the stale-entry rule permits since the pair is real. That a routine written twice scores 0.31 is this file's own argument made concrete: two copies drift apart in structure as well as text, so the metric loses confidence exactly as the problem gets worse. Most of the difference is renaming -- prevButtons/previousButtons, btnDefs/buttonDefinitions, prevTrigDown/triggerDown -- which is exactly the tidying this file's header says the fingerprint was designed to see through, and it still scored low enough to hide under the old bar for the entire life of the gate. The genuine differences are bolted onto the ends: the shell has a settings chord and ControllerTestGui, the companion has CompanionDisabled, EnablePersistentMouseMode, the diagnostic trigger pair and ActiveInputBackend. Those are additions to a common loop, not two loops. This is the merge with the most value and the most risk in the project: it is the input path of a program that runs as the Windows shell, so it needs hardware behind it and not a review.
QuickMenuEnsureContentFits: 0.40, and what is left of the pair is a wrapper each. The body is QuickMenuFitContent in SteamShell-Common.ahk; these two resolve which work area to centre on and whether to re-centre when the content already fits, then call it. THE EARLIER VERSION OF THIS ENTRY WAS WRONG, and the way it was wrong is worth more than the entry. It said the real difference was where the work area comes from -- the shell asks the monitor of QuickMenuPreviousHwnd, the companion its stored QuickMenuMonitorIndex -- and called that real per-tree state. It is: it is also four numbers, and the shared file's own header names passing a value as a parameter as one of the three remedies. Nobody asked whether it could be one. So the measurement, the requirement, the work-area clamp, the centring and the log stayed duplicated behind a difference that was never load-bearing, and when the requirement turned out to be one pixel wrong at 300% scale it had to be fixed in both copies in the same commit -- after logging a Warning on every Quick Menu open for as long as anyone had been looking at the log. THE ONE DIFFERENCE THAT IS REAL is the re-centre: the shell moves unconditionally, because that is how its menu follows the foreground window's monitor, and the companion returns once the content fits, because Xbox FSE owns presentation and there is no foreground window to follow. That is a boolean the caller decides, and it is why these two wrappers exist rather than one shared entry point.
QuickMenuHandleController: 0.73, and the only one of the eleven that was already above the old bar -- it was simply never listed. Genuine: the shell owns a TASKS page with select-to-lock, tap-X-to-close and hold-X-to-force-close, so it takes a `released` mask and keeps three more statics that the companion has no page to use them on. The B-button branch was NOT genuine and is gone: it restated the MAIN-page test that shared QuickMenuGoBack already makes, and now calls it bare as the companion always did.
ReloadSettings: 0.47. Same three opening moves -- reload the file, re-arm the timers, rebuild the Quick Menu if it is open -- and then each product resynchronises what it owns. The shell reapplies SafeMode overrides, syncs the elevated input helper, un-hides the cursor if auto-hide was switched off, and refreshes the Control Panel and the Always Focus lists. The companion clears the GameInput failure latch so the backend can be retried without a restart, syncs the elevated RTSS helper, and repopulates its Settings window. Nothing here is shared logic wearing two names. Minor drift worth noting: the same event notifies at "Success" in the shell and "Info" in the companion.
TrayOpenSettings: two lines each, calling ShowSettingsEditor and ShowSettings. The two Settings surfaces are separate implementations, which ProductSettingsScrollBar already records; this is that same divergence seen from the tray. It merges when they do, and not before.

# ------------------------------------------------------------------------------
# WHAT THIS FILE STILL CANNOT SEE
# ------------------------------------------------------------------------------
# Lowering the bar to 0.45 closed one blind spot. It does not close the other,
# and the other is the one that produced the worse bug.
#
# THE GATE COMPARES FUNCTIONS. The same reasoning written INLINE in both trees is
# not below the threshold -- it is unreachable by any check in this file, at any
# threshold, because there is no pair to score.
#
# GameShapeFactsForWindow was exactly that. Both trees built the facts map for the
# shared GameWindowShapeVerdict inline: the companion per-monitor, the shell
# against A_Screen* only. So a fullscreen game on a second monitor was measured
# against the first monitor's size at an origin of (1920, 0), failed the position
# tolerance, and scored as borderless or was rejected outright -- in the product
# that is the Windows shell. A comment in the companion recorded this as
# deliberate, in the form of an assertion about the OTHER tree: "the shell can
# assume the game is on A_Screen*". It cannot. It centres its own GUIs per
# monitor and resolves a monitor index for the foreground window.
#
# It is one shared function now. The general rule it earned:
#
#   A SHARED ARBITER FED BY TWO PRIVATE ARGUMENT BUILDERS IS A DUPLICATE WITH
#   EXTRA STEPS. Sharing the function that decides is worth little if each tree
#   assembles what it decides on, and nothing in this file will ever notice.
#
# Worth auditing on the same basis, none of them yet checked: every other shared
# function that takes a facts or weights map assembled by its caller.
#
# And the rule that covers both blind spots: a divergence is only intentional if
# someone wrote down WHY. A comment in one tree asserting something about the
# other tree is the weakest form of that -- it reads as a decision, it is checked
# by nothing, and it ages into a false statement without anyone editing it.
ControllerBindingLabels: 1.00, and a data table rather than a routine -- a static Map and a return, which is why it scores what ProductIdentity scores and for the same reason. It is the list of builtin actions each product offers and the words it calls them by, and BOTH halves are per-product. The companion speaks Xbox FSE's vocabulary ("Game Bar", "Back / Escape", "Close window") because a user reading it has not been looking at a Windows desktop; the shell uses Windows' own names because it IS the Windows shell. The action SETS differ too: TaskView, WindowsDesktop and Settings exist only in the companion, ControlPanel only in the shell, and ProductControllerBindingAction is already the seam that executes them. What used to be duplicated was the LOOKUP, in both directions, in both products -- four hand-kept tables that could disagree. That is SharedBindingLabelFor and SharedBindingActionFor in SteamShell-Common.ahk now, and the reverse direction is derived by inverting this table rather than typed again. Not a seam entry: shared code never calls this, the tree passes it in.
